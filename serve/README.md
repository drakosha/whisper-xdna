# Serving it

`npu_stt_server.py` wraps the encoder in an HTTP endpoint that speaks the same
multipart contract as `whisper.cpp`'s `/inference`, so an existing client can be
pointed at it without changes:

```
POST /inference
  file            audio (wav / webm / ogg)
  response_format json
  audio_ctx       encoder positions to compute (see below)
  language        e.g. ru
→ {"text": "..."}
```

The pipeline inside is: audio → mel → **encoder on the NPU** → decoder on the
CPU, both halves out of the checkpoint `NPU_STT_MODEL` names (`large-v3-turbo`
by default).

**Both halves have to come from the same checkpoint.** Feeding the
`large-v3-turbo` encoder's output to a `large-v3` decoder produces garbage while
the cosine stays unchanged — the failure is a silently wrong transcription, not
an error. Taking the weights out of the loaded model rather than a separate
`.npz` is what makes that mismatch unrepresentable; `NPU_STT_WEIGHTS` is the one
way back into it, so an `.npz` there must match the model you name.

`tiny`, `small`, `large-v3` and `large-v3-turbo` have all been run end to end
through this path; the mel bin count follows the checkpoint, so 80-mel and
128-mel models both work.

## Starting it

```bash
RENDER_GID=$(getent group render | cut -d: -f3) WITH_REFERENCE=1 \
  docker compose up -d stt
```

The first start downloads the `large-v3-turbo` checkpoint (~1.6 GB), lifts the
encoder half out of it as fp32 and uploads it to the device; the torch encoder
is dropped before the decoder ever runs, so the 635M parameters that would
never execute are not kept. Then it compiles an overlay set per context on the
ladder, which is minutes cold and seconds after. Both caches live in named
volumes, so a container restart pays neither again.

Nothing has to be generated by hand. `NPU_STT_WEIGHTS` still accepts an `.npz`
from `tools/dump_ref.py --model large-v3-turbo` if the machine cannot reach
the internet.

## Two details that cost a day to find

**One process, one venv.** The encoder needs numpy, `ml_dtypes` and `pyxrt`; the
mel and the decoder need torch and `openai-whisper`. Rather than two processes
and a socket, both live in the torch venv — `rawxrt` only shells out to IRON for
compilation, which is a subprocess anyway. Verify this on your own setup rather
than assuming: under the serving interpreter the acceptance suite must still
give the same bit-identical result.

**Changing `audio_ctx` between requests will kill the NPU path** if you do not
unload the old geometry first: `DRM_IOCTL_AMDXDNA_CREATE_HWCTX IOCTL failed
(err=-22)`, after which the internal flags stay off for the life of the process
and everything runs on the host path (3.3 s → 18.3 s). Unloading costs ~500 ms
on the first request after a switch.

The subtle part: the unload must drop the scratch buffers *and* their views
along with the contexts. Sub-BOs carved out of an fc2 design's `A` buffer
survive the context going away, the next pass allocates a new one, and fc1 then
writes into nothing — **timings stay normal and the text comes back silently
wrong** (English output for Russian speech). A speed benchmark does not see
this. Only comparing the output does.

## `audio_ctx` matters more than you would think

Whisper always pads its input to a 30 s window = 1500 encoder positions, but you
can compute fewer. On this hardware, against `whisper.cpp` on the same machine:

| `audio_ctx` | NPU encoder | whisper.cpp encode | speedup |
|---|---|---|---|
| 512 | 1582 ms | 2074 ms | 1.31x |
| 768 | 2267 ms | 3282 ms | 1.45x |
| 1024 | 2456 ms | 4377 ms | 1.79x |
| 1500 | 3346 ms | 6969 ms | 2.09x |

The wall-clock advantage shrinks toward short contexts; CPU occupancy does not
(0.25 of a core against 13–15 at every context). If your workload is short
utterances, the reason to use this is the *cores*, not the latency.

Clients should size `audio_ctx` to the actual speech length — but note that
truncating below the speech length makes Whisper's decoder loop on the tail
(1217 decode steps instead of 103 on a 22.6 s clip), so leave headroom.

## Falling back to a CPU implementation

Set `STT_CPU_URL` to a `whisper.cpp` `/inference` endpoint and the server will
route to it rather than fail or make the caller wait:

- **NPU path raised** — the request is proxied, the caller gets a normal `200`
  with correct text (~2.15 s), and the log carries the traceback plus
  `FALLBACK->CPU [error]`. Silent degradation is the thing to avoid here: a
  fallback nobody notices is how you end up shipping the slow path for weeks.
- **Audio would not decode** — also proxied, because the two ffmpeg builds do
  not fail on the same inputs; costs 29 ms to find out.
- **The device is busy** — the second concurrent request goes to the CPU
  immediately rather than queueing. `STT_BUSY_WAIT_MS` sets how long to wait for
  the device first; **0 measured best on the tail** (worst-of-pair 4.06 s → 2.70 s),
  while a long wait wins on the *median* (the winner of the pair gets 1.94 s,
  the best number in the table). Pick by which one your users feel.

Empty `STT_CPU_URL` (the default) disables all of this.

Two details worth copying: the proxy forwards the **original request bytes**, so
the CPU response is byte-identical to what the caller would have got hitting
that endpoint directly; and every response carries `X-STT-Path: npu|cpu`, with
counters (`served_npu`, `busy`, `error`, `decode`, `proxy_failed`) on `/health`,
so the fallback rate is visible instead of inferred.

Note the responses are *not* normalised between paths: `whisper.cpp` returns a
leading space and a trailing newline, this server does not. Clients that
`.strip()` will not notice; clients that do not, will.

Keep a fallback in the client too. Serving-side fallback covers a sick NPU; it
cannot cover the server process being dead.

## Long recordings

Whisper sees 30 s at a time, so anything longer is cut into windows and the
device runs them back to back under one lock. Measured on this machine, a
304 s clip at `audio_ctx=1500`:

| | |
|---|---|
| windows | 10 |
| encoder | 33.7 s (10 x ~3.4 s) |
| decoder | 5.6 s |
| mel | 22 ms |
| **wall clock** | **39.4 s** |

Two consequences worth knowing before pointing a client at it. The whole
request holds the device, so a second caller during those 39 s gets the CPU
fallback (or a 503 with no `STT_CPU_URL`). And 39 s is past the timeout most
clients give an HTTP request -- a 30 s client budget covers roughly 3.5 minutes
of speech, so long audio wants a longer timeout on the caller's side.

`NPU_STT_MAX_WINDOWS` (default 20, i.e. 10 minutes) truncates beyond that
rather than holding the device indefinitely; the response then carries
`X-STT-Truncated-S` with the number of seconds dropped, and the log says so.

## Known limits

- Speech longer than 30 s is windowed with a fixed stride, while `whisper.cpp`
  advances the window by timestamps. Text agrees inside a window and diverges at
  the seam.
- The decoder, not the encoder, is now the bottleneck: torch fp32 costs 2.4 s on
  a 22.6 s clip against 338 ms for whisper.cpp's quantised decoder — 42% of
  end-to-end. Threads do not help (the decode is latency-bound, 103 sequential
  steps); the wall is flat at 4/8/16.
- The process holds ~12.7 GB resident (weights plus the torch decoder).

## Units

`units/npu-stt.service` starts the `stt` service from the repo's `compose.yml`
at boot, which is the whole of it — compose publishes the port itself. It
expects the checkout in `/opt/npu-whisper` and `RENDER_GID` in
`/etc/default/npu-stt`; both are one line to change.
